# Changelog

## Unreleased

- **Stored Files Never Run As The Site (R2-001, security, pairs with DjangoLux's scaffold proxy)**: a stack-schema-4 proxy served an uploaded `.html` or `.svg` from `/media/` inline, with no CSP, no `nosniff` and no `Content-Disposition`, so its script ran as the site with the rights of whoever opened it. `media_migration.serving_gaps` names what a private proxy file does not send: `X-Content-Type-Options`, `Content-Security-Policy` or `Content-Disposition` on `/media/`, or the maintenance page's CSP. `harden` adds them to the generated shape in place, schema unchanged: the `(dlux_media_headers)` snippet and its `import` in both Caddy `/media/` routes, or the `$dlux_media_csp` / `$dlux_media_disposition` maps and `add_header` lines in every nginx `/media/` location. The schema 3 migration emits the same blocks. The `stored-files` check is a SECURITY FAIL naming each missing header and file (a WARN when only the maintenance CSP is missing). `check --fix` applies it on any DjangoLux, validates, archives and recreates the proxy; a route with its own serving headers is left to a human with copy instructions. `inspect` returns `gaps` and `hardenable`; `tests/fixtures/schema-4` carries the hardened proxy and `schema-4-unhardened` the earlier one. `scripts/scaffold_alignment.py` prints `aligned` against the paired DjangoLux scaffold. Docs: `docs/proxy.md` § How stored files are served, `docs/check.md` § `stored-files`.
- **Maintenance Page CSP On Existing Stacks (R2-022, proxy half)**: the same `check --fix` adds `Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' data:; font-src 'self'; connect-src 'self'; base-uri 'none'; form-action 'none'; frame-ancestors 'self'` to the Caddy `/_dlux/maintenance/*` route and `handle @down` page, and to the nginx `/_dlux/maintenance/` and `/dlux-maintenance.html` locations (`always`), matching DjangoLux's scaffold. Where the override page lives stays with `maintenance_page.py`.

## v1.11.0b2

- **`update self` Takes Wrapper 7's `--pin` (F1, blocker)**: the launcher routed `update … self` through `_update_self_help_args`, which accepted only `-h`/`--help` and the global `-f`/`-d`, so wrapper 7's own `update self --pin` (and `--allow-downgrade`, `--allow-unverified-composer`) got the usage line and exit 2, and every `./start.sh update self` failed. `launcher._update_self_args` now passes every option `cli.update_self_options()` reads from the `update self` parser through to `handle_update_self`, and still refuses service names and update options. `tests/test_wrapper_pin.py` runs the real `start.sh` against the real launcher; `scripts/smoke-test.sh` runs `./start.sh update self` through the wrapper without `COMPOSER_SELF_IMAGE`. A stack pinned at 1.11.0b1 moves on with `./start.sh agent update`.
- **No Pin On A Release From Before Signing (F2, O6)**: `image_pin.resolve` refuses to pin a Composer older than 1.11.0b1, verified or not, `--allow-unverified-composer` included: it has no `org.dlux.composer.image-pin` label, cannot read a digest-pinned block and never moves the pin, so `check --stable` while stable was 1.10.4 left the wrapper on 1.10.4 for good. The refusal (`predates_pinning_refusal`, `PinError.way_out`) says to stay on beta until 1.11.0 stable, before anything changes; `pin_composer_image` and `switch_composer_channel` refuse such a pin too, and `check --fix` never pins the block to such a lock (`fix:composer-pin` warns). `composer-channel` warns on such a lock with the way out, `docker pull debeski/composer:beta` then `COMPOSER_SELF_IMAGE=debeski/composer:beta ./start.sh check --beta -y` (`docs/updates.md`, "Releases before signing").
- **Fresh Non-Root Install Starts (exit 78)**: on empty volumes `app_permissions.run` skipped `static` and `dlux_runtime`, which the first `up` then created from a plain `USER 10001:0` image's root 0755 mount points, so the entrypoint gate exited 78. Before the pre-up grant, `ensure_for_image` now has Compose create the app services' containers and their missing volumes (`create_app_volumes`: `up --no-start --no-deps --no-recreate`, Compose's own labels, Docker's fill from the image), then grants, then `up` starts the same containers.
- **Channel Switch Recreates The Pair (O4)**: `check --beta` / `--stable` retagged the block and wrote the lock but left `composer-agent` and `composer-executor` on the old image. `_switch_channel` now runs the `check --fix` lifecycle step (`_finish_fix`) on the switch: the pair is recreated and waited for, or recorded as `pending-recreate`. `composer-channel` compares the image each running resident container was created from with the lock (`_resident_running_images`) and warns, with `./start.sh`, when they differ.
- **Plain Text For The Operations Panel (O3)**: `output_utils.strip_terminal_controls` removes escape sequences (colours, `ESC[2K`, cursor moves, OSC) and control characters. `logs_tail` strips them in the executor (`ops._read_logs`) and again on the agent side (`ops._tail_logs`), and `OpsResponder.answer` publishes every string of a result (findings, repair notes and diffs, logs, the error) as plain text.
- **Docs Say Where The Pin Edit Is Kept (O1)**: the original `compose.yml` of a pin or channel switch is kept under `.xclude/dlux-agent-bootstrap/<UTC>/` (`agent_installer._backup_root`), not `.xclude/composer-check/`; `docs/updates.md` and `docs/check.md` now say so.
- **The Downgrade Record Names The Deployed Image (O5)**: `deployed.json` keeps the baked DjangoLux after an inline update by design; the guard still holds because DjangoLux's supervisor serves a volume release only while it is newer than the baked package and the floor check refuses an image below the active release. The record is described as the newest image deployed (`docs/deploying.md`, `downgrade_guard` docstring); its format is unchanged.

- **`check --fix` Asks At A Terminal, Never Elsewhere (stack recovery B)**: new `composer/guidance.py`. With a terminal on stdin and without `-y`, `COMPOSER_ASSUME_YES`, `--json` or the resident pair (`guidance.interactive`), `check --fix` asks the operator-choice findings as short questions before it plans (`CheckupMixin._ask_operator_questions`), each with the recommended answer on Enter and `s` to skip: how users reach the server when `front-proxy` warns about an unset `DLUX_FRONT_PROXY` (`1` a front proxy, addresses checked with `front_proxy.parse_ranges`; `2` directly, empty; `3`, the default, `private_ranges`), which updates the app may request when the secrets file sets no valid `DLUX_UPDATE_POLICY` (default the policy in force), and whether to switch Redis to snapshots when `redis-persistence` warns (`n` keeps the append-only file). Answers join the plan: the one confirmation lists them, and the values are written first (`fix:secrets`, `guidance.set_secret_values`): in place like the stamp repair, one line replaced or appended, owner, mode, inode and line endings kept, never copied to the archive, a value with a quote, `#`, a backslash or a line break refused; the recreate then reads them (`_deployment_environment` adds them over what `./start.sh` passed). Scripted, agent and panel runs ask nothing and behave as before. New `redis-aof-corrupt` finding: FAIL when `redis` restarts or exited and its log shows Redis's own append-only-file error; `check --fix` stops it, moves the append-only files into `aof-archive/<UTC>/` on the same volume with a one-off `docker run --rm --network none --pull never` container that mounts only that volume (nothing deleted), switches to snapshots and recreates `redis` even with `--no-recreate`. Scaffold alignment stays `aligned`, with `redis-persistence` OK on a fresh project and an append-only line caught as drift.
- **`check --fix` Finishes What It Changes (stack recovery A)**: after its one confirmation, `check --fix` now brings the running stack to the files it wrote, in the same run. Before the first write it reads the resolved Compose model (with the deployment's secrets) and the containers (`CheckupMixin._lifecycle_baseline`); after the repairs it compares the model one service at a time, key order aside (new `composer/stack_lifecycle.py`). Every repair that drops a service now stops and removes its container with `docker compose rm -s -f` while the file still defines it, writing nothing if that fails: `_apply_stack_migration` does it for every service the transform drops (`agent_installer._remove_service_containers`, was `docker-socket-proxy` only), so a retired `dlux-updater` and a replaced `composer-updater` no longer keep running orphaned; whatever is still left is found by Compose's project and service labels and stopped and removed (`fix:remove-services`, volumes kept). Running services whose definition changed, and services added to a running stack, are recreated with `recreate_containers()` (`up -d --no-deps --force-recreate`, start-up steps run) under the deployment's secrets (refused without them), skipping what a repair already recreated, then health-checked alone with the settle window (`fix:recreate`); a service whose unchanged image tag now names another image than it runs is held back, so `check --fix` never deploys an image on the side. `composer-executor` and `composer-agent` are recreated last from a terminal (`fix:recreate-resident`); an Operations panel apply runs inside them (the executor's sibling now runs `check --fix -y --resident-apply`), so it leaves them and records them in `.xclude/composer-check/pending-recreate.json`, which the new `pending-recreate` finding reports until their containers are replaced. The confirmation lists the services removed, the ones expected to be recreated and the restart window; the Operations preview ends with `remove-services` and `recreate-services` entries from the same plan (`CheckupMixin._fix_plan`, split out of `_maybe_fix`; `planned_lifecycle`). New `check --no-recreate` keeps the files-only behaviour (dropped services are still removed); `-y` still recreates. Every remaining step printed is a `./start.sh` command: the `redeploy_command` hints of `agent enable`, `executor enable`, the init-container retirement, the install, the channel switch and the pin are `./start.sh` (`./start.sh -d` for the dev override), and the fix messages no longer print raw `docker compose` commands.
- **Deployment Update Policy (pairs with DjangoLux 1.17.0)**: new `DLUX_UPDATE_POLICY` (`all` default, `inline`, `none`; unknown counts as `none`), read by the resident pair from its own Compose environment (`composer/update_policy.py`). Under `inline` the image trigger is answered with exit 2 and a policy message instead of running `composer update` (watcher and executor loop), `agent-update` is refused by the agent's ops handler and by the executor's `agent_update`, and a control-link `recovery_deploy` is refused by the agent and the executor; `none` also refuses inline package applies (package trigger and `dlux_package_apply`). - **Health Must Hold, Not Just Be Seen Once (break-it #3)**: `HealthMonitorMixin.monitor_health` passed on the first poll that found every service healthy, so a crash-looping container without a healthcheck (Decrees' `celery` after Celery was dropped, `No module named celery`) passed or failed depending on when the poll landed. A service now passes once it is healthy and its newest container has been up for a settle window (`COMPOSER_HEALTH_SETTLE_SECONDS`, default 10, `0` off), measured from that container's own `StartedAt` (`started_epoch`, `container_uptime`; the first healthy poll when it cannot be read or is ahead of Composer's clock): a container already up that long adds no wait, one that just started is watched until it gets there. A service that leaves healthy meanwhile fails, and any container restart from the first poll on fails the run: a higher `RestartCount` or new `StartedAt` (`DockerComposeMixin.container_restart_markers`, one `docker inspect` per poll) or a poll that finds it `restarting`. The failure names the service and its last log lines (`collect_service_diagnostics(log_services=…)`; restarting services, and services still starting at the timeout, now get logs too), the likely cause when the logs or exit code show one (new `composer/failure_hints.py`: a missing Python module such as a leftover `celery`, another CPU architecture, a missing command, a port in use, an unreachable database or Redis, a schema that does not match, incomplete settings, a permission problem, exit 137), and the next steps (`./start.sh logs SERVICE`, `COMPOSER_EXCLUDE_SERVICES=SERVICE` in the secrets file). Applies to deploys, `update`, `restart` and inline DjangoLux updates.

The baked DjangoLux version is also refused below the image floor of the runtime volume's active release (`requires.baked_image`, legacy `image_baseline`, in `releases/<active>/dlux/release-manifest.json`), read by `runtime_release_floor` in a throwaway Composer container (`--pull never`, `--network none`, volume read-only, only an existing volume): an image older than DjangoLux 1.17 runs a supervisor that never checks it. A release before `SIGNED_SINCE` (1.11.0b1) is never fetched: switching to one says it predates signed releases and needs `--allow-unverified-composer`. `Resolution.pin` may now be None; `update_pin` then changes no file. Wrapper 7 (`start.sh`, `start.ps1`, still unpublished, so no new marker) keeps the deployer it installed when `update self --pin` pins nothing, instead of failing "the deployer reported a pin, but .composer-image is unreadable". - **Composer Pins Its Own Image To A Signed Digest ("mutable refs")**: the deployer and the resident pair ran `debeski/composer:latest`/`:beta`, so whoever could push those tags chose the next image of a process holding the Docker socket. The release workflow now pushes only `:vX.Y.Z`, writes `composer-image.json` (version, tag, index digest, prerelease), signs it keylessly with Sigstore as `release.yml` on that tag (new `sign` job, the only one with `id-token: write`), attaches it and its bundle to the GitHub Release, and only then moves `:latest`/`:beta` onto that digest (new `aliases` job, `imagetools create`). New `composer/image_pin.py` reads the channel tag's version label as a hint, downloads that release's statement and bundle (redirects only to GitHub's asset hosts, bounded), verifies the bundle with `sigstore verify identity` against `…/.github/workflows/release.yml@refs/tags/vX.Y.Z` (online, then `--offline`) and checks the statement names that version, and records `debeski/composer:vX.Y.Z@sha256:…` in the new `.composer-image` lock. `update self` (`--pin` writes only the pin), `agent update` and `check --beta|--stable` resolve and apply it (`agent_installer.pin_composer_image`: block retag validated, lock after); a channel older than the pin changes nothing (a tag never moves a pin backwards) unless `--allow-downgrade` or a channel switch asks for it; an unreachable GitHub or Sigstore refuses unless `--allow-unverified-composer` / `COMPOSER_ALLOW_UNVERIFIED_COMPOSER=1`, which pins the registry digest of the release's own tag and never overrides a failed signature. `channel_config.resolve_self_image` takes the lock after `COMPOSER_SELF_IMAGE`. The `composer-channel` finding compares the block with the lock (a project with no lock on its channel tag is OK, so a fresh scaffold stays aligned) and `check --fix` pins the block to an existing lock without network access; the Operations preview shows that repair (`composer-pin`). The executor's `agent_update` helper mounts the project read-write over its read-only mount so the pin can be written. `agent-check` reads the published version from the channel tag, not from the pin. The image names `sigstore>=4.6,<5` and carries `org.dlux.composer.image-pin="1"`.

- **Agent Reads Docker Through The Executor; No Docker Proxy (composer-hardening item 7)**: a compromised `composer-agent` could read every container's environment (database password, `SECRET_KEY`) and files through the read-only `docker-socket-proxy`, because `CONTAINERS=1` opens every `GET` under `/containers` and `docker compose ps`/`logs` need `GET /containers/{id}/json`, which a path allow-list cannot narrow. The agent now has no Docker access: three new executor operations (`executor_protocol.READ_OPS`) answer its reads with bare fields: `services_state` (name, state, health, status, restart label), `logs_tail` (a deployment service or all, 1–1000 lines, redacted in the executor and fitted to one frame) and `image_digests` (`RepoDigests` of `WEB_IMAGE`, `COMPOSER_CHECK_IMAGE` or a `--check-image` only). `ops._service_table`, `ops._tail_logs` and `watcher._local_repo_digest` call them through `executor_client.read` (`reads_via_executor`; the executor marks itself with `COMPOSER_IN_EXECUTOR` and reads Docker directly). Reads skip the write lease, capped at two at once, so the Operations card and the update check work during a deploy; an executor without the reads says to update both resident services. `agent_installer._hardened_stack` no longer generates the proxy, the agent's `DOCKER_HOST` or its `depends_on` entry. `check` reports a read-only proxy beside `composer-executor` as a `docker-proxy` WARN (a write-enabled one stays FAIL); `check --fix` (resident-block repair, `executor enable`, `agent enable`) removes it with `_drop_docker_proxy`, and `_apply_stack_migration` runs `docker compose rm -s -f docker-socket-proxy` before writing (a deploy keeps orphans running, and the container would stay reachable on `docker_proxy`), writing nothing if that fails. Pairs with DjangoLux 1.17.0, whose scaffold drops the proxy; `scripts/scaffold_alignment.py` prints `aligned` for the pair.
- **Scaffold Alignment Gate (owner: "imperative")**: new `scripts/scaffold_alignment.py` generates a project from a DjangoLux checkout. It fails on any `check` FAIL, any WARN outside the live-stack or operator-choice set, any repair that would rewrite a file, and any `start.sh` / `start.ps1` that differs from Composer's. `tests/test_scaffold_alignment.py` runs it against the sibling checkout (`DLUX_CHECKOUT`), including drift cases (a split stamp, a stale wrapper), and skips in CI. `docs/RELEASING.md` makes it a paired-release step and corrects the scaffold wrapper path.

A panel apply runs `check --fix`, so the operator now sees those diffs before applying them.
- **Package Availability And Deploy Status Written Without Following Symlinks (assembly)**: `dlux_package_cli.write_availability` and `_publish` (`state/package-available.json`, `deploy-status.json` on the shared runtime volume) now use `safe_files.atomic_write_json`, so a symlink an app service planted at the target or its temp name is replaced, not written through.
- **A Failed Deploy Keeps The Proxy Up (break-it #10)**: after a failed health check `caddy` stayed "Created" (it depends on `web`) and the site was fully down with no maintenance page. After `up`, and again when `up` or the health check fails, `DockerComposeMixin.ensure_edge_proxy` starts any edge proxy in scope (`caddy`, `nginx`, `proxy`) that is not running with `docker compose up -d --no-deps`, so it serves the maintenance page on 502/503/504; the failure message says whether the proxy is up (`keep_site_reachable`). The failed containers are left for diagnosis; restoring the previous image after its successor migrated would itself be a downgrade.
- **Pinned And Unpinned DjangoLux Resolution Through PyPI CDN Lag**: a pinned `dlux update --version X` right after X was published failed "not published", and `dlux check` said "up to date", while PyPI's CDN still served a stale index (seen 2026-10-09 and 2026-11-25). `dlux_release_source.resolve_candidate` now backs `describe` and `obtain`: a pin the index lacks is read from its own release page (`/pypi/django-lux/<version>/json`, cached apart and fresh), with re-reads after 3, 6 and 12 s before "not published"; an unpinned resolve also probes the release pages of the likely next releases (`likely_successors`: the final of a newest beta, the next patch/minor/major, and next betas on the beta channel) and of the release the last check offered. A release page gets the index's trust (approved HTTPS host, SHA-256, then attestation); yanked releases are ignored; probe failures are not errors; channel and quarantine still decide.
- **Registry Login Directory Removed On SIGTERM**: `registry_login.docker_config` relied on `atexit`, which a signal skips, so a SIGTERM during a deploy left the temporary `DOCKER_CONFIG` (holding the registry login) behind. A SIGTERM handler now removes it and then runs the previous handler (the process still dies of SIGTERM), and each new directory is named `composer-registry-<pid>-…` so the next process sweeps directories whose process is gone (SIGKILL, crash), including its own pid's leftover from an earlier container start.
- **Version Gate Fails Closed On A Missing Label**: once `COMPOSER_ACTIVE_VERSION_FILE` enables the gate, a target image without a readable `COMPOSER_VERSION_LABEL` version (missing, or not a version) used to pass with a note. `VersionGateMixin.preflight_version_gate` now refuses, names the label and the images it checked, and says to rebuild with the label or re-run with `--force`, the deliberate override. A missing `active.json` also passed, which left every stack without an inline update with no downgrade guard: the active version now falls back to the version label of the image the app container runs (`running_image_version`, via `compose ps --all -q` and `docker inspect`), matching how DjangoLux reads a missing `active.json`. Only a stack with no app container passes without one; an unreadable file or an unlabelled running image refuses unless `--force`.
- **Shared-Volume Writes Without Predictable Temp Names**: writers on the runtime volume opened fixed temp names (`.x.json.tmp`, `.x.<pid>.tmp`, `.wheel.part`) with `open("w")`, so a symlink an app service planted there redirected Composer's write onto its target. New `composer/safe_files.py` writes through an exclusively created random temp file and renames it over the target; used by the agent's bridge documents, the executor's `agent_update` helper, the downloaded wheel, `watcher` (availability, ack, terminal status), `ops`, `dlux_channel` and `relay`. Documents other services write (bridge results, `snapshot.json`, `enroll-request.json`) are read with `O_NOFOLLOW`, regular files only, at most 64 KiB (snapshot 256 KiB).
